# Model 310.9.16: the October weight set

Status: 2026-10-19. Read from public sources and other forks; **not yet run here**. The menu change below is built and
host-tested against 310.8.2.0. Nothing in this note has been measured on this machine or on Rafael's.

## What it is

- NVIDIA announced a faster DLSS 5 model on 2026-10-13: about half the GPU cost of the September model, 24% fewer
  parameters (about 118 M), 20% less VRAM at 4K, "comparable visual fidelity" (NVIDIA's claim). It reaches games
  officially through NBA 2K27, RTX Remix (2026-10-23) and Hogwarts Legacy (2026-11-05).
- The DLL is `nvngx_dlssnr.dll` **310.9.16.0**, taken out of the NBA 2K27 update on 2026-10-16:
  266,424,944 bytes, SHA-256 `2BC19BC09A7B89DD44F73E2AC0108FCC586E2154BDD0830F242F4F040E28789F`, signed by NVIDIA
  on 2026-09-25 (openNR's README and the Aurora X fork's notes). It is **not** in the DLSS SDK v310.9.16 release
  on GitHub, which carries `nvngx_dlss`, `nvngx_dlssd` and `nvngx_dlssg` only (checked 2026-10-19).
- As shipped it requires Blackwell. `clshortfuse/openNR` (`ea0d7e0`, 2026-10-16) added the profile
  `compat-fp16-310.9.16`, which rebuilds it for RTX 20/30/40 from that exact input with CUDA 13.4.3 tools; its
  reference output is SHA-256 `CDFA6C1EC784867182164C7836F324F087B5C9F374D0C9FE46F54999FEABF3ED`. ShortFuse posted
  the built DLL (`nvngx_dlssnr_compat-fp16-310.9.16-cuda13.4.3`) on the RenoDX Discord. By Aurora X's byte
  comparison the patch lowers the D3D11/D3D12 architecture gates, moves seven main-network kernels into a new
  `.nrcubin` section with sm_75/86/89 cubins, rebuilds eight small kernels in place, drops the signature, and
  leaves both weight sets and the remaining code untouched. openNR claims D3D11/D3D12 only: **the Vulkan route
  (DOOM Eternal here) is unclaimed.**

## Two weight sets, and what the preset does

| Weight set | Name in the model | In |
|---|---|---|
| September | `CC_Control_History_Blend_Quantize_With_Teacher_honest_tench_2026_07_04_22_30_weights` (`WEIGHTS_HT`) | 310.8, 310.9.16 |
| October | `hnet-crazy-cuckoo-small-fp8` (`WEIGHTS_CC_SMALL_FP8`) | 310.9.16 |

The September name is in 310.8.2.0 here, and the 2026-09-21 Windows trace (below) shows 310.8 listing it as its one
config with backbone "crazy-cuckoo". The October name comes from ShyVortex's reverse-engineering note
(`docs/issues/NR/NR-LIGHTWEIGHT-MODEL-PRESET-SUPPORT.md` in their fork) and agrees with Aurora X's. Both report, from `CG2RFindWeightByPreset`, that preset 0 (Default) and preset 2 select the October set,
preset 1 the September set, and preset 3 is undocumented. The press calls them "Preset A" (previous) and "Preset B"
(new, default). None of this has been read from 310.9.16 here.

Measured elsewhere, not here: Aurora X on an RTX 4090 (Hogwarts Legacy, working scale 0.5) had one pass at
5.52 ms with the September set and 3.46 ms with the October set; two October passes 6.55 ms. Press tests report
30-40% higher frame rates in modded games and one user found the effect "softer, less aggressive".

## What changed here

The preset combo already appears once the model reports more than one weight set (`DlssNr::ModelLog::ConfigCount`,
since 310.8 reports one). What it lacked was the answer to "which one is running": a preset number means something
different per model, and the model falls back silently. The model can say it itself, through lines `ModelLog`
routes into `OptiScaler.log` (its printf formats, all four present in 310.8.2.0):

```
DLSSNR: %zu config(s) available:
DLSSNR:   [%zu] %s (backbone: %s)
DLSSNR: Created feature %u (output %ux%u, network %ux%u, preset=%d -> %s)
DLSSNR: BuildActiveNetwork config=%s N=%d W=%d H=%d
```

`DlssNr_ModelLogParse.h` reads them; `ModelLog::ConfigNames()` and `ModelLog::Active()` keep the list, the last
built set and the preset its create line names; the panel shows **Running: <weight set> (preset N)** under the
preset combo (and under the one-weight-set line), the two known sets named in words and anything else by its raw
name, with a tooltip listing what the model carries. Nothing is sent to the model that was not sent before, so with
NR off the behaviour is unchanged.

**But no Proton run here has shown one of these lines.** `ModelLog::Install` logs that it hooked
`OutputDebugStringA/W`, and then nothing follows, in Crimson Desert, Stellar Blade, Generation Zero or Rafael's
Monster Hunter Wilds logs. They were seen once, on Windows on 2026-09-21 (neural-amd's ETS2 trace, `preset=1 ->`
the September set), with NGX logging switched on. The model reads `LogLevel`, `EnableConsoleLogging`, `LogPath`
and `EnableLogPathOverride` under `HKLM\SOFTWARE\NVIDIA Corporation\Global\NGXCore` (wide strings in 310.8.2.0,
`RegQueryValueExW` imported), and nothing here sets them, which is the likely reason; not yet tested. Until it is,
the Running line stays absent, and `ConfigCount()` stays -1, which keeps the preset combo visible: the right
default for 310.9.16, where there is something to choose. The test is one `LogLevel` value in the game's prefix
for one run, then deleted; if the model then also writes a log file beside the game, that is what the setting costs.

`tests/nr-model-loader` covers the parsing and, on the real model file (`NR_MODEL_DLL`), that the four formats are
still in it. Run it against a 310.9.16 file before installing it.

## Still to verify with the file in hand

0. The model's own lines: one run with `LogLevel` set in the game's prefix (above), to read "N config(s)
   available", both names, and which set Default, Preset 1 and Preset 2 create.
1. The suite against the file (`NR_MODEL_DLL=<path> python3 tests/nr-model-loader/run.py`): import slots for
   `ModelLoader=direct`, and the three log formats.
2. Crimson Desert (D3D12, forwarder): GPU time per preset (the panel's GPU timing), and an A/B of the look.
3. DOOM Eternal (native Vulkan): whether the compat build creates the feature at all.
4. The D3D11 bridge (Divinity) and the Vulkan present host.
5. Rafael's RTX 3060: the compat build is FP16 on Ampere; 310.8's FP16 path there is the baseline in
   [model-cost-across-architectures.md](model-cost-across-architectures.md).
6. [vit-skip.md](vit-skip.md) step 2: janblade found (`d810d066d`, 2026-10-17) that on DLLs built on the 310.9 host
   a decoder buffer starts inside the ViT run's 1-D result, so reusing the run's last kernel rebuilds the
   bottleneck from foreign data; they reuse through their own copy of the run's 2-D output instead. Any skip
   designed against 310.8 must be re-checked on 310.9.16.

`DLSSNR.MaskBlendMode`, which one fork (`Dr-Arayashiki`, `c4b9d7050`) writes for "310.9.16+", comes with no evidence
that the model reads it; it is not taken.
