# Model 310.9.16: the October weight set

Status: 2026-10-19. Read from public sources, other forks and, for the preset table and `MaskBlendMode`, the
310.9.16.0 binary itself; **not yet run here**. The menu change below is built and
host-tested against 310.8.2.0. Nothing in this note has been measured on this machine or on Rafael's, apart from one
Rafael data point added on 2026-10-29 (under "Field reports").

## What it is

- NVIDIA announced a faster DLSS 5 model on 2026-10-13: about half the GPU cost of the September model, 24% fewer
  parameters (about 118 M), 20% less VRAM at 4K, "comparable visual fidelity" (NVIDIA's claim). It reaches games
  officially through NBA 2K27, RTX Remix (2026-10-23) and Hogwarts Legacy (2026-11-05).
- The DLL is `nvngx_dlssnr.dll` **310.9.16.0**, taken out of the NBA 2K27 update on 2026-10-16:
  266,424,944 bytes, SHA-256 `2BC19BC09A7B89DD44F73E2AC0108FCC586E2154BDD0830F242F4F040E28789F`, signed by NVIDIA
  on 2026-09-25 (openNR's README and the Aurora X fork's notes). It is **not** in the DLSS SDK v310.9.16 release
  on GitHub, which carries `nvngx_dlss`, `nvngx_dlssd` and `nvngx_dlssg` only (checked 2026-10-19).
- As shipped it requires Blackwell. `clshortfuse/openNR` (`ea0d7e0`, 2026-10-16) added the profile
  `compat-fp16-310.9.16`, which rebuilds it for RTX 20/30/40 from that exact input with CUDA 13.4.3 tools; its
  reference output is SHA-256 `CDFA6C1EC784867182164C7836F324F087B5C9F374D0C9FE46F54999FEABF3ED`. ShortFuse posted
  the built DLL (`nvngx_dlssnr_compat-fp16-310.9.16-cuda13.4.3`) on the RenoDX Discord. By Aurora X's byte
  comparison the patch lowers the D3D11/D3D12 architecture gates, moves seven main-network kernels into a new
  `.nrcubin` section with sm_75/86/89 cubins, rebuilds eight small kernels in place, drops the signature, and
  leaves both weight sets and the remaining code untouched. openNR claims D3D11/D3D12 only: **the Vulkan route
  (DOOM Eternal here) is unclaimed.**

## Two weight sets, and what the preset does

| Weight set | Name in the model | In |
|---|---|---|
| September | `CC_Control_History_Blend_Quantize_With_Teacher_honest_tench_2026_07_04_22_30_weights` (`WEIGHTS_HT`) | 310.8, 310.9.16 |
| October | `hnet-crazy-cuckoo-small-fp8` (`WEIGHTS_CC_SMALL_FP8`) | 310.9.16 |

The September name is in 310.8.2.0 here, and the 2026-09-21 Windows trace (below) shows 310.8 listing it as its one
config with backbone "crazy-cuckoo".

**Which preset selects which set, read from 310.9.16.0 (official, `2BC19BC0...`) on 2026-10-19.**
`CG2RFindWeightByPreset` (RVA `0x23c20`, source `rel_310_9/.../dlssnr/cg2r_weights.cpp`) walks a two-entry table at
VA `0x1800dbe30` (0x290 bytes per entry, preset id at +8):

| Entry | Preset id | Name | Tag | Backbone |
|---|---|---|---|---|
| 0 | 1 | `CC_Control_History_Blend_Quantize_With_Teacher_honest_tench_2026_07_04_22_30_weights` | `WEIGHTS_HT` | `CC_SILVER_AARDWOLD` |
| 1 | 2 | `hnet-crazy-cuckoo-small-fp8` | `WEIGHTS_CC_SMALL_FP8` | `CC_SMALL_FP8` |

Any other preset (0 = Default, 3) is not found and falls back to "shipping default preset 2", logging
`preset %d is not available in this DLL build; falling back to shipping default preset %d ('%s')`. So **Preset 1 is
the September set, Preset 2 and everything else the October set.** This agrees with ShyVortex's note
(`docs/issues/NR/NR-LIGHTWEIGHT-MODEL-PRESET-SUPPORT.md` in their fork) and Aurora X's. The press calls them
"Preset A" (previous) and "Preset B" (new, default).

Measured elsewhere, not here: Aurora X on an RTX 4090 (Hogwarts Legacy, working scale 0.5) had one pass at
5.52 ms with the September set and 3.46 ms with the October set; two October passes 6.55 ms. Press tests report
30-40% higher frame rates in modded games and one user found the effect "softer, less aggressive".

## What changed here

The preset combo already appears once the model reports more than one weight set (`DlssNr::ModelLog::ConfigCount`,
since 310.8 reports one). What it lacked was the answer to "which one is running": a preset number means something
different per model, and the model falls back silently. The model can say it itself, through lines `ModelLog`
routes into `OptiScaler.log` (its printf formats, all four present in 310.8.2.0):

```
DLSSNR: %zu config(s) available:
DLSSNR:   [%zu] %s (backbone: %s)
DLSSNR: Created feature %u (output %ux%u, network %ux%u, preset=%d -> %s)
DLSSNR: BuildActiveNetwork config=%s N=%d W=%d H=%d
```

`DlssNr_ModelLogParse.h` reads them; `ModelLog::ConfigNames()` and `ModelLog::Active()` keep the list, the last
built set and the preset its create line names; the panel shows **Running: <weight set> (preset N)** under the
preset combo (and under the one-weight-set line), the two known sets named in words and anything else by its raw
name, with a tooltip listing what the model carries. Nothing is sent to the model that was not sent before, so with
NR off the behaviour is unchanged.

**But no Proton run here has shown one of these lines.** `ModelLog::Install` logs that it hooked
`OutputDebugStringA/W`, and then nothing follows, in Crimson Desert, Stellar Blade, Generation Zero or Rafael's
Monster Hunter Wilds logs. They were seen once, on Windows on 2026-09-21 (neural-amd's ETS2 trace, `preset=1 ->`
the September set), with NGX logging switched on. The model reads `LogLevel`, `EnableConsoleLogging`, `LogPath`
and `EnableLogPathOverride` under `HKLM\SOFTWARE\NVIDIA Corporation\Global\NGXCore` (wide strings in 310.8.2.0,
`RegQueryValueExW` imported), and nothing here sets them, which is the likely reason; not yet tested. Until it is,
the Running line stays absent, and `ConfigCount()` stays -1, which keeps the preset combo visible: the right
default for 310.9.16, where there is something to choose. The test is one `LogLevel` value in the game's prefix
for one run, then deleted; if the model then also writes a log file beside the game, that is what the setting costs.

`tests/nr-model-loader` covers the parsing and, on the real model file (`NR_MODEL_DLL`), that the four formats are
still in it. Run it against a 310.9.16 file before installing it.

## Still to verify with the file in hand

0. The model's own lines: one run with `LogLevel` set in the game's prefix (above), to see the table above
   come back from the running model.
1. Done 2026-10-19: the suite against the compat build (`NR_MODEL_DLL=<path> python3 tests/nr-model-loader/run.py`)
   passes, with one W and one A caller-path slot for `ModelLoader=direct` and all four log formats. The compat
   build's SHA-256 is openNR's reference output exactly, and the official input's is openNR's pinned input.
2. Crimson Desert (D3D12, forwarder): GPU time per preset (the panel's GPU timing), and an A/B of the look.
3. DOOM Eternal (native Vulkan): whether the compat build creates the feature at all.
4. The D3D11 bridge (Divinity) and the Vulkan present host.
5. Rafael's RTX 3060: the compat build is FP16 on Ampere; 310.8's FP16 path there is the baseline in
   [model-cost-across-architectures.md](model-cost-across-architectures.md).
6. [vit-skip.md](vit-skip.md) step 2: janblade found (`d810d066d`, 2026-10-17) that on DLLs built on the 310.9 host
   a decoder buffer starts inside the ViT run's 1-D result, so reusing the run's last kernel rebuilds the
   bottleneck from foreign data; they reuse through their own copy of the run's 2-D output instead. Any skip
   designed against 310.8 must be re-checked on 310.9.16.

`DLSSNR.MaskBlendMode` is real: it is the one `DLSSNR.*` parameter 310.9.16.0 reads that 310.8.2.0 does not (an
earlier version of this note said there was no evidence for it; the binary is the evidence). Its parameter read
(RVA `0x1ab30`) stores it next to `UseAutoMask`, resets anything above 3 to 0, and then, when the application gave a
`DLSSNR.ControlMask` resource and the mode is 0, turns the auto skin mask off; modes 1 to 3 keep both masks (how they
combine is not read). **Retoque passes no `ControlMask`**, so the mode changes nothing here and is not sent. One fork
(`Dr-Arayashiki`, `c4b9d7050`) writes it without a mask, which has no effect either.

The other differences in the model's strings against 310.8.2.0: a "guided upsample" with a high-resolution source
(`dlssnr_guided_high_source_scratch`, RGBA16F) is new, and `PollRuntimeParams`, the per-frame
`enabled=... localTone=...` line and the capacity probe on resize are gone.

## Field reports from other projects (2026-10-29)

**These are third-party reports, not measured here.** They come from `perseval-BLR/DLSS5-NeuralScreen`, read in a
clone. NeuralScreen runs NVIDIA's NR runtime over the whole Windows desktop, not inside a game. Its licence is
PolyForm Strict 1.0.0, which forbids copying or building on its code. The reports are cited here, and none of its
code is in this tree.

- **RTX 3090, device removed under NR** (`bffd0ae`, 2026-10-20, their issue #181, NeuralScreen 2.6.1). The D3D12
  device was removed with `0x887A0007`, a driver reset, somewhere between 12 s and 48 min into NR, and DRED recorded
  no page fault. Their own restart then came too early: `D3D12CreateDevice` still returned `0x887A0004` while the
  driver recovered, and three times the whole PC froze on a black screen. Their fix waits for the driver before
  restarting and, on a pre-Blackwell card, which their runtime reaches "through the architecture patch", leaves NR
  off after a second reset in one session. The commit says plainly that the reset is inside NVIDIA's runtime on
  Ampere and is not fixed by it. **Which model** that user ran is not stated. NeuralScreen's bundled runtime was
  310.8.0.0 at the time (their `CHANGELOG.md:75`), the unpatched build that
  [ngx-driver-616.md](ngx-driver-616.md) already refuses on the loader route, but a user can put another one in
  `native\libraries\`. So the report cannot be pinned to either weight set or to the compat build.
- **Official 310.9.16 on an RTX 3060 Ti: `CreateFeature` returns PlatformError** (`0d4f0bc`, 2026-10-19, their issue
  #175). With the official `nvngx_dlssnr.dll` 310.9.16 dropped in, the card passed their signature gate and
  `Init_Ext`, then `CreateFeature` answered `0xBAD00002` (`NVSDK_NGX_Result_FAIL_PlatformError`). Their fix falls
  back to the bundled 310.8, "which runs on Ampere". This is the "as shipped it requires Blackwell" above, seen from
  the outside: the refusal arrives at create, not at load or init.

**What it means here.** On Ampere, a refused create is the expected result with the official file, and only the
openNR compat build or 310.8.x is expected to create at all. A clean create still says nothing about stability over
time: the 3090 report fails after minutes, with nothing DRED can name, which no short session here would catch. The
forwarder's `__try` (CLAUDE.md, "A fault inside the model") covers a CPU-side fault in the model's code. It does not
cover a GPU reset, which comes back to the game as a removed device.

**Our one Ampere data point with a 310.9.16 file** (measured, Rafael's RTX 3060, driver 617.14, Mortal Shell II,
2026-10-29; `~/.local/state/dlss5/deployments/rafael-logs-20261029-ms2/OptiScaler.log:716`, `:946`). The model was
`nvngx_dlssnr.dll` 310.9.16.0 at **276,162,560 bytes**, not the official 266,424,944. Its hash was not logged, so the
file is not identified beyond its size. NGX's loader 32.0.16.1714 routed feature 18 itself. Over about a minute and a
half of NR, the pass recorded `model_ok=3108 model_failed=0` at a 960x540 working size, with no device removal in
the log. That is one short session. It does not answer the 3090 report.

## Driver overrides (2026-10-30)

**Host-tested only; not run in a game or against a driver that sets them.** R610 added three NR settings to the
driver profile, and dxvk-nvapi v0.9.3 (2026-10-30) answers them on Proton from `DXVK_NVAPI_DRS_<name>` or
`DXVK_NVAPI_DRS_SETTINGS`. Ids and values from `NvApiDriverSettings.h` at NVIDIA/nvapi `87dca625` (R615, the
headers dxvk-nvapi v0.9.3 builds with; its `src/util/util_drs.h` names the same values); the vendored
`external/nvapi` predates them:

| Setting | Id | Values |
|---|---|---|
| `NGX_DLSS_NR_OVERRIDE` ("Enable DLSS NR override") | `0x10E41E04` | 0 off (default), 1 on |
| `NGX_DLSS_NR_OVERRIDE_RENDER_PRESET_SELECTION` ("Override DLSS NR presets") | `0x10E41DF8` | 0 off (default), 1-4 A-D, `0xFFFFFF` latest |
| `NGX_DLSS_NR_SL_OVERRIDE` ("Enable DLSS NR SL override") | `0x10E41E05` | 0 off (default), 1 on |

`SL_DLSS_OVERRIDE` (R615) is `0x10E41E06`, which `NvApiHooks` already answers 0 for while DLSS-G is OptiScaler's FG
output; that is unchanged.

**Who reads the preset selection.** 310.8.2.0 and 310.8.3.0 read it themselves: two `mov ecx, 0x10E41DF8` before
calls to a DWORD-setting reader (310.8.3.0 at VA `0x18001841b`), and a non-zero answer goes to a callback with
feature id 18, kind 3, or 7 for latest. Whether the model then uses it as its preset, and whether that reader goes
through the hooked `nvapi_QueryInterface`, is not read. The 310.9.16.0 build here (276,162,560 bytes) has no such
immediate. So on the forwarder route the model itself can see the override, not only the NGX loader.

**What changed.** `DlssNr_DrsOverride.h`, called from `NvApiHooks::hkNvAPI_DRS_GetSetting`. With `[DlssNr] Enabled`
on, the preset selection is reported to its reader as off, as SR and RR already are, so `[DlssNr] Preset` stays the
only preset choice. Each NR setting's value is logged at its first read and when it changes (`DLSS-NR: driver setting ...`). The
two enable switches are logged and not changed: turning them off would act on the driver's choice of model file,
which is not established. Unlike SR, the external NR preset is not adopted when `Preset` is left at 0; mapping A-D
onto the model's preset ids 1 and 2 is unverified. With NR off the three settings pass as before and nothing is
logged. `tests/nr-drs-override` holds both. To check it: a game with `DXVK_NVAPI_DRS_NGX_DLSS_NR_OVERRIDE_RENDER_PRESET_SELECTION=render_preset_a`
and NR on should log the line and keep the **Running** preset the menu names.
